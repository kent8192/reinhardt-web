# Command-aware management bootstrap

Generated Pages and RESTful projects now use the capability-aware management
entry point. Existing applications can migrate without changing their
`BaseCommand` implementations or their old launchers immediately.

## Migrate a management launcher

Keep the existing `get_settings()` function for strict runtime commands. Move
its source configuration into one reusable `settings_builder()` function and
add `get_scoped_settings()` returning `settings_builder().build_scoped()`. The
builder must use the same defaults, profile, TOML files, and environment source
order in both paths. A scoped path parses TOML syntax and merges values first;
it expands environment references and deserializes only requested effective
settings paths. Missing or invalid selected values fail. An eager-only custom
source must implement `ConfigSource::load_scoped`; the default reports an error
with migration guidance.

Implement `CapabilityProvider` in the native `manage` binary with
`type Settings = ProjectSettings`, `scoped_settings()` calling
`get_scoped_settings()`, and `full_settings()` calling `get_settings()`. Pass it
and the command registry to `execute_from_command_line_with_capabilities` (or
`execute_from_command_line_with_capabilities_and_shell` for a shell-enabled
launcher). Pass the existing `CargoCheckContext` so `verify` can replay the
consumer build. The generated template contains a complete example.

`collectstatic` and `buildstatic` now need `[static].root` or
`[static_files].root` on this path. A legacy `static_root` key is also accepted.
The static URL defaults to `/static/`; explicit invalid values do not silently
fall back. Their selected settings are validated without constructing runtime
JWT/session/database settings or starting application services. `runserver`
and legacy commands still resolve full settings. The existing eager entry
points retain their behavior, including source loading and migration fallback.

## Opt in a custom command

Implement `CapabilityCommand::cli()` with a clap `Command` definition. After
the shared dispatcher parses its arguments, `requirements()` returns
`CapabilityRequirement::settings::<MyView>(alias)` and/or
`CapabilityRequirement::service::<MyService>(name, alias)`. A `SettingsView`
resolves and validates its declared paths using `ScopedSettings::require_path`
or `optional_path`; profile-dependent validation can inspect `profile()`.
Register the command with `CommandRegistry::register_capability`.

The provider's `prepare_service()` receives each declared service after every
settings view has validated. It may read already prepared values from the
`CapabilityContext` and returns a typed `Arc` as `PreparedValue`. The context
prepares one resource per type/alias pair and owns it through execution. Access
to an undeclared capability fails with a declaration hint. Implement resource
shutdown in the service's `Drop` implementation or owned RAII guards; partial
preparation failure releases the resources already stored in the context.
Service preparation follows the order of the command's declarations; this API
does not create a general dependency graph.

## Choose migration state explicitly

On the new launcher, ordinary `makemigrations` defaults to
`--state-source temporary-db`. Use `--state-source files` for offline replay or
`--state-source database --database ALIAS` for one configured database. The
`default` alias is used when `--database` is omitted. `--check`, `--empty`, and
`--merge` do not initialize a database; `--force-empty-state` uses an explicit
empty state. The parser rejects incompatible combinations before loading
settings. The selected source fails without falling back to another source.
`--dry-run` changes file writes only, not the state source.

## Validate a consumer before removing build secrets

Run the actual generated or custom management binary with runtime JWT,
session, and database secrets unset. Confirm that `collectstatic` produces the
expected assets, malformed static inputs fail, and no PostgreSQL, Redis, or
unrelated provider is contacted. In a separate invocation, confirm that
`runserver` rejects missing runtime secrets. Only then remove temporary
build-only secrets from the consumer's Dockerfile. This framework change does
not modify a Cloud consumer or guarantee offline availability of Rust compiler
dependencies or optional vendor assets.
