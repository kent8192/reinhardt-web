# String primary-key conversion compatibility in 0.4.0

Models with `PrimaryKey = String` accept raw `String` and `&str` values through
`IntoPrimaryKey<T>`. This allows generated relationship and Info builders to
accept text keys without loading the related model:

```rust,ignore
let connection = Connection::build().node("peer-001").finish();
let info = ConnectionInfo::build().id(None).node(String::from("peer-001")).finish();
```

## Source compatibility

The upstream implementations overlap with previously legal downstream
implementations of `IntoPrimaryKey<Peer>` for `String` and `&str`. Recompiling
such a consumer produces E0119. Their addition is a breaking change even though
the trait's signature and existing setter names did not change.

PR #6423 introduced these implementations; the `reinhardt-db@v0.4.0-alpha.18`
tag already contains them. Remove overlapping implementations before compiling
against any revision containing this change. There is no deprecation period:
Rust rejects overlapping trait implementations before executing any code.

## Remove identity conversions

Delete both implementations when they only return the same text:

```rust,ignore
impl IntoPrimaryKey<Peer> for String {
    fn into_primary_key(self) -> String { self }
}

impl IntoPrimaryKey<Peer> for &str {
    fn into_primary_key(self) -> String { self.to_owned() }
}
```

Existing calls to `.node(key)` then use the framework implementations. Owned
strings move into storage; borrowed strings are copied. Empty text, whitespace,
leading zeros, and Unicode remain unchanged. Model-reference calls such as
`.node(&peer)` continue to work. No database migration is needed.

## Preserve application-specific conversions

Move normalization or other custom conversion logic to a local newtype.
Removing an implementation that changed the key without moving its logic would
silently change application behavior.

```rust,ignore
use reinhardt::db::orm::IntoPrimaryKey;

struct NormalizedPeerKey<'a>(&'a str);

impl IntoPrimaryKey<Peer> for NormalizedPeerKey<'_> {
    fn into_primary_key(self) -> String {
        self.0.trim().to_owned()
    }
}

let connection = Connection::build()
    .node(NormalizedPeerKey(" peer-001 "))
    .finish();
assert_eq!(connection.node_id(), "peer-001");

let info = ConnectionInfo::build()
    .id(None)
    .node(NormalizedPeerKey(" peer-001 "))
    .finish();
assert_eq!(info.node.id, "peer-001");
```

The framework does not implement `IntoPrimaryKey<Peer>` for application-owned
newtypes. This preserves the downstream extension point without changing the
model's stored primary-key type.

## Design rationale

The existing setter bound is `Key: IntoPrimaryKey<Peer>`. Supporting a raw text
value through that bound requires the same trait/type combination that a
consumer may already implement. Under Rust trait coherence, overlapping
implementations cannot coexist.
The existing trait bound cannot choose a framework identity conversion only
when a downstream implementation is absent.

| Alternative | Compatibility and API effect |
| --- | --- |
| Framework-owned text-key wrapper | Avoids occupying downstream text implementations, but removing the raw implementations breaks current calls and requires callers to wrap their keys. |
| Separate raw-key setters | Can preserve older custom implementations, but replaces the existing raw-key call path and expands generated relationship and Info builder APIs. |
| Another conversion trait with a blanket legacy adapter | The adapter and raw-string route overlap again when the consumer supplies a legacy text implementation. |

Retaining raw text conversion keeps the generated-builder use case from #6409
supported with the existing call syntax. The compatibility cost is explicit:
identity implementations must be removed, and custom behavior must move to a
newtype. Local SemVer tooling alone cannot establish compatibility with every
legal downstream trait implementation.

See the [Rust Reference on trait coherence](https://doc.rust-lang.org/reference/items/implementations.html#trait-implementation-coherence),
[Issue #6429](https://github.com/kent8192/reinhardt-web/issues/6429) and the
[original implementation](https://github.com/kent8192/reinhardt-web/pull/6423).
