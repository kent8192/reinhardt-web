# Typed SQLite Database-List Inspection

**Issue:** [#6508](https://github.com/kent8192/reinhardt-web/issues/6508)

**Parent migration:** [#5895](https://github.com/kent8192/reinhardt-web/issues/5895)

**Status:** Implemented; local validation complete.

**Date:** 2026-10-04

## Evidence

The inspected develop baseline is
`ab21faf668cec073798fa2c3a09f6d6bf70687d8`.
[`SqliteDurableJobStore::reject_private_in_memory_pool`](../../crates/reinhardt-tasks/src/durable.rs)
executes a connection-local database-list command, detects an empty filename on
the main database, and then evaluates the pool's maximum connection count and
schema sharing. The query crate has no dedicated typed representation for this
inspection at that baseline.

SQLite defines this list as belonging to the current connection. An empty
filename means that the listed database is not associated with a file; it does
not identify whether a pool shares that database. See the
[SQLite database_list specification](https://www.sqlite.org/pragma.html#pragma_database_list)
and [in-memory database documentation](https://www.sqlite.org/inmemorydb.html).

## Accepted Scope

Add a dedicated, backend-checked SQLite database-list inspection operation to
`reinhardt-query` and replace this one command in `SqliteDurableJobStore`.
This is a backward-compatible capability addition for `develop/0.4.0`.

Foreign-key connection control belongs to
[#6499](https://github.com/kent8192/reinhardt-web/issues/6499). Pool probe cleanup
belongs to [#6497](https://github.com/kent8192/reinhardt-web/issues/6497).
This slice does not redesign either behavior or migrate unrelated task SQL.

## Accepted Pool Compatibility

- Inspect the main database by its name, independently of attachment rows.
- Preserve the empty-filename trigger and the subsequent schema-sharing check.
- Permit a private in-memory pool with a maximum of one connection.
- Permit a shared in-memory pool with multiple connections.
- Reject a private in-memory pool with multiple possible connections using the
  existing error behavior and message.
- Preserve the existing executor and pool/connection ownership.

## Checked Statement API

`Query::sqlite_database_list()` constructs a no-argument
`SqliteDatabaseListStatement`. The statement exposes these methods, each
returning `Result<(String, Values), QueryBuildError>`:

| Method | Result |
| --- | --- |
| `build_sqlite_checked()` | `PRAGMA database_list` and empty `Values` |
| `build_postgres_checked()` | `UnsupportedBackendFeature` for PostgreSQL |
| `build_mysql_checked()` | `UnsupportedBackendFeature` for MySQL |
| `build_cockroachdb_checked()` | `UnsupportedBackendFeature` for CockroachDB |

Use the existing `QueryBuildError::UnsupportedBackendFeature` variant. Do not
add a new error enum or implement `QueryStatementBuilder`, whose unchecked
methods cannot express the required fallible backend validation. There is no
arbitrary PRAGMA name, option string, schema qualifier, or raw-expression input.

The query layer owns the command text. A crate-private SQLite renderer can
generate it without adding required methods to existing public backend traits.
Add the statement in `crates/reinhardt-query/src/query/sqlite_database_list.rs`
and follow the crate's existing query, root, and prelude re-export conventions.
No new feature flag or runtime dependency is needed.

All public statement construction and SQL-generation symbols have P2
native/WASM parity. They acquire no connections, execute no database commands,
and perform no filesystem or transaction operations on either target.

## Result Contract

Return the original database-list result without projection, filtering,
renaming, sorting, or filename normalization.

| Column | SQLx decoding type | Meaning |
| --- | --- | --- |
| `seq` | `i64` | SQLite's database sequence identifier |
| `name` | `String` | `main`, `temp`, or the attached database's name |
| `file` | `String` | SQLite's reported filename, including the empty string |

The result-column order remains `seq`, `name`, `file`. The durable store continues
to read `name` and `file` by name and does not infer the main database from a row
position or an attachment's filename. Preserve SQLite's sequence values without
promising stable attachment identifiers across attachment changes.

SQLx remains the executor and decoder. Do not add a public result-row DTO or a
SQLx dependency to the query crate's production dependencies. The generated SQL
is still connection-local: executing it through a pool describes the selected
connection, not all connections in that pool.

## Durable Store Integration

Replace only the hand-authored database-list command in
`SqliteDurableJobStore::reject_private_in_memory_pool` with the SQL generated by
`build_sqlite_checked()`. Retain the existing `fetch_all(&self.pool)` execution,
row decoding, maximum-connection check, schema-sharing probe, and rejection
message. Preserve SQLx failures as `DurableQueueError::Database`; propagate any
query-construction failure through the existing `DurableQueueError::Store`
category without adding a public error variant or introducing a panic.

The list operation does not prove that a pool is shared. A database row with an
empty filename only triggers the existing pool safety check when its name is
`main`. An empty filename on an attached database or the TEMP database must not
trigger that check by itself.

## Verification and Removal Conditions

Component coverage belongs in the owning crate. New tests that integrate
multiple Reinhardt crates belong under `tests/`. Use `rstest`, precise
assertions, independently scoped connections, and RAII-owned temporary files.

Required behavior coverage:

1. Assert the exact SQLite command and empty bind values; check the typed
   unsupported-feature error for all three other backends before execution.
2. Prove that the statement has no unchecked generic build path, using an
   appropriate compile-fail case.
3. Execute generated SQL against SQLite and assert all three column names,
   column order, decoding types, and expected values.
4. Inspect file-backed and in-memory main databases, a file-backed attachment,
   and an in-memory attachment. Create TEMP objects explicitly before asserting
   a TEMP database row. Compare returned filenames with the fixture's actual
   filesystem path rather than normalizing the production result.
5. Hold two connections simultaneously, attach a database only to one, and
   verify that its attachment is absent from the other connection's list.
6. Preserve these existing regressions:
   `from_pool_rejects_private_in_memory_sqlite_pool`,
   `from_pool_allows_shared_in_memory_sqlite_pool`, and
   `from_pool_allows_single_connection_private_in_memory_sqlite_pool`.
7. Verify that a file-backed main database with an in-memory attachment is
   accepted by `SqliteDurableJobStore::from_pool` and remains usable. Hold
   attachment setup on the inspected connection; a single-connection pool is
   sufficient for this regression.

For implementation, complete affected crate tests/checks, formatting and lint
checks, query documentation builds and doctests, a native/WASM compile check of
the pure SQL-generation surface, and the required local SemVer check. Check the
query crate with its default features and `thread-safe`, and the tasks consumer
with `durable` enabled. No external database service is needed for these SQLite
regressions.

Retire the exact Workaround annotation and the corresponding #5895 inventory
entry only after the typed operation, caller replacement, and required behavior
regressions pass. If the baseline has no annotation or inventory entry, do not
add a transient exception merely to remove it. Coordinate the matching audit
update with the #5895 migration without modifying its other worktree or retiring
the separately tracked #6497 and #6499 exceptions.

unchanged.

baseline. The operational command in `durable.rs` now uses the typed operation;
the remaining literal is owned by the query renderer.
